== Secret Service Integration
This feature allows KeePassXC to act as a Secret Service provider over DBus. It enables applications to store and retrieve secrets securely via the https://www.freedesktop.org/wiki/Specifications/secret-storage-spec/[Secret Storage specification]. While running, KeePassXC acts as a Secret Service server registered on DBus so clients like seahorse, python-secretstorage, secret-tool, or other implementations can connect and access the exposed database in KeePassXC.

=== Enabling the Integration
Only one secret service provider can be enabled at a time. You may have to disable other providers, such as GNOME Keyring or KWallet, to use KeePassXC as a secret service provider. You will see a notice when attempting to enable KeePassXC as the secret service provider if another is already running.

To replace most third party secret service providers with KeePassXC, run the following shell snippet:

```bash
mkdir -p "${XDG_DATA_HOME:-${HOME}/.local/share}/dbus-1/services"
cat > "${XDG_DATA_HOME:-${HOME}/.local/share}/dbus-1/services/org.freedesktop.secrets.service" <<EOF
[D-BUS Service]
Name=org.freedesktop.secrets
Exec=/usr/bin/keepassxc
EOF
```

NOTE: You may need to restart your session or log out and back in for the changes to take effect.

1. Open KeePassXC → **Tools → Settings → Secret Service** → check **Enable KeePassXC Freedesktop.org Secret Service integration**. Then press OK to save this setting and enable the integration. Go back into this settings screen to see currently open databases that you can unlock and edit their exposure to secret service.

=== Granting Access
With **Confirm when passwords are retrieved by clients** enabled, KeePassXC shows an access request whenever a client asks for a password that it has no decision for:

.Secret Service Access Request
image::secretservice_access_dialog.png[]

The decision has two parts. **Allow** and **Deny** answer the request for the checked entries, and **Deny for this program** next to an entry settles that one entry on its own.

**Scope** decides how far the answer reaches:

* **Once** covers this request, and the next one asks again.
* **Selected** stores the answer for the entries listed above. It applies to the same application from then on, across restarts of both KeePassXC and the client, which is what makes short-lived clients workable with confirmations turned on: they are recognized by what they are rather than by the process they happen to run in.
* **Selected + future** stores it for those entries and for every other entry the application asks for, including entries created later.

An entry denied with **Deny for this program** keeps that denial under every scope. Under **Selected + future** this is how "everything except this one" is expressed: the entry's own decision outranks the one covering the rest.

**Details** shows the process the request came from together with its parents, which is also where a stored decision gets its shape:

.Access Request Details
image::secretservice_access_details.png[]

The **Match** column selects which of those processes the stored decision is anchored on, and is available for the scopes that store something. Only the calling process is selected. KeePassXC warns when the request deserves a second look:

* An unreadable or non-existing executable path means the client cannot be identified reliably.
* The caller is a general purpose tool: a script interpreter such as `python3`, a shell, or a command line client such as `secret-tool`. It asks on behalf of whatever invoked it, so a stored decision authorizes every use of that tool by any program.
* An executable whose content changed since the decision was stored is marked on the affected rows. This is what an update of the client looks like, and also what an impostor at the same path looks like, so the decision has to be made again.

When any of these apply, **Scope** starts at **Once**, which is also the recommended answer. No selection of processes makes a general purpose tool identify the program behind it.

==== Narrowing a Decision With an Ancestor

There is a way to narrow a stored decision further, and it fits one shape: an ancestor that has an executable of its own and exists to do a single job, which reaches for a secret through a general purpose tool. A compiled program of yours that calls `secret-tool` is such an ancestor. Ticking it in the **Match** column adds it to the rule, which from then on matches only clients started by it.

A script is not such an ancestor. Running a script executes its interpreter, so the executable of that process is `/bin/bash` or `/usr/bin/python3`, and that is what a condition on it would match — the general purpose tool again, under a different name. Which script is running appears only in the command line, which is shown in the details for you to read and is never matched on: a process can rewrite its own command line at will.

Conditions apply to a position in the process tree, not to the tree as a whole. A condition on the parent matches clients whose parent is that executable, and one two levels up matches clients exactly two levels below it. Anchoring on `init` therefore does not cover everything in the session, and a rule stops matching when the same program is started through a different chain, from a terminal instead of a service, for example.

Judgement is what makes this work, and general purpose tools are a broader family than script interpreters: shells, `secret-tool`, `dbus-send`, `busctl`, `xargs`, `env` and anything else that runs or asks on behalf of whoever called it. When the ancestor you are about to tick is one of those, the rule has not become any narrower. When in doubt, answer **Once**.

WARNING: A rule you write yourself is applied exactly as written. Use at your own risk.

=== Managing Stored Decisions
Stored decisions live in the database they concern, not in the application settings, and are managed in **Database → Database Settings → Secret Service**. Each row is one client the database recognizes, with what identifies it and what it may do:

.Client Authorizations
image::secretservice_database_settings.png[]

**Edit** opens the client, where the matching rules and the decision for entries without one of their own can be changed:

.Client Authorization Editor
image::secretservice_client_record.png[]

A client matches when it satisfies every condition of at least one rule. A condition applies to one process of the client's process tree — the caller, its parent, and so on — and requires a matching executable path, executable file name, or SHA-256 digest of the executable content. Digests are what turn an update of the client into a new access request; paths and names alone do not.

TIP: Two records can be written so that the same client matches both. KeePassXC points this out and resolves it in a fixed order — a record denying everything wins, otherwise the record created first — but it is worth removing the ambiguity.

Decisions for individual entries are shown on the entry itself, under **Secret Service**, where they can be changed and removed:

.Entry Access Decisions
image::secretservice_entry_settings.png[]

The Authorization tab of **Tools → Settings → Secret Service** lists the applications currently connected and which stored client each one is recognized as:

=== Limits of Client Recognition

WARNING: A stored decision is a convenience, and it is not an authentication mechanism. Understand what it can and cannot tell apart before you store one.

A client is recognized by its executable path and by the content of that executable, read through `/proc`. That much survives the client restarting or getting a new process ID, and it tells an updated or replaced binary from the one that was authorized.

Everything below defeats it:

* Code injected into a legitimate client, for example through `LD_PRELOAD` or a plugin it loads, runs as that client and inherits its authorizations.
* Two scripts run by the same interpreter look identical: both processes run the interpreter's executable, and the script's path is part of the command line, which is not matched on. Only an ancestor with an executable of its own can tell them apart.
* A process whose executable `/proc` does not reveal, such as one with `PR_SET_DUMPABLE` cleared or one owned by another user, is never recognized and asks every time.
* Any user who can write the client's executable, or place their own executable at that path, becomes that client as far as KeePassXC can tell.

Grant a stored decision the way you would grant the password itself: to a program you would hand it to anyway.

=== Implementation Details

* The user can specify the database and group that is exposed to the service.
* Desktop notifications when a secret is retrieved and access confirmation dialogs.
* `FdoSecrets::Service` is the top level DBus service. There is one  `FdoSecrets::Collection` per opened database tab and each entry under the exposed database group has a corresponding `FdoSecrets::Item` DBus object.
* The following entry attributes are exposed to the secret service: Title, Username, Password, URL, Notes, TOTP, and non-protected Custom Attributes.
* Stored decisions are kept in the database: the client and its rules in the database's custom data, the decision for an individual entry on that entry. Older KeePassXC versions keep them intact, but merging a database with one of those versions can drop them, in which case the client asks again.
