== Secret Service Integration
This feature allows KeePassXC to act as a Secret Service provider over DBus. It enables applications to store and retrieve secrets securely via the https://www.freedesktop.org/wiki/Specifications/secret-storage-spec/[Secret Storage specification]. While running, KeePassXC acts as a Secret Service server registered on DBus so clients like seahorse, python-secretstorage, secret-tool, or other implementations can connect and access the exposed database in KeePassXC.

=== Enabling the Integration
Only one secret service provider can be enabled at a time. You may have to disable other providers, such as GNOME Keyring or KWallet, to use KeePassXC as a secret service provider. You will see a notice when attempting to enable KeePassXC as the secret service provider if another is already running.

To replace most third party secret service providers with KeePassXC, run the following shell snippet:

```bash
mkdir -p "${XDG_DATA_HOME:-${HOME}/.local/share}/dbus-1/services"
cat > "${XDG_DATA_HOME:-${HOME}/.local/share}/dbus-1/services/org.freedesktop.secrets.service" <<EOF
[D-BUS Service]
Name=org.freedesktop.secrets
Exec=/usr/bin/keepassxc
EOF
```

NOTE: You may need to restart your session or log out and back in for the changes to take effect.

1. Open KeePassXC → **Tools → Settings → Secret Service** → check **Enable KeePassXC Freedesktop.org Secret Service integration**. Then press OK to save this setting and enable the integration. Go back into this settings screen to see currently open databases that you can unlock and edit their exposure to secret service.
+

2. Either click the pencil icon in the previous settings screen, or go to **Database → Database Settings → Secret Service**. Enable **Expose entries under this group**, and select the desired group. All entries within this group and all subgroups will be exposed to the service.

3. Use apps that integrate with secret service to start saving and using credentials within KeePassXC. If you enabled confirmation prior to access, you will see the access request dialog described below.

=== Granting Access
With **Confirm when passwords are retrieved by clients** enabled, KeePassXC asks for your permission before it hands out a password that has no stored decision:

.Secret Service Access Request
image::secretservice_access_dialog.png[]

From top to bottom, the dialog shows:

* The client that is asking: its name, the path of its executable, and its process ID. Anything unusual about the client is listed right below, one line each; these notes are explained in the next section.
* The database the request is about and the requested entries in it, one per row with its icon, title and username. The check box selects the entries your answer applies to; every row starts checked, and clicking anywhere in a row toggles it. The row below the entries, **… and all entries requested in the future**, stands for everything else the client may ask for later.
* **Remember**, which stores your answer in the database.
* **Details**, which shows the processes behind the request, and the **Allow** and **Deny** buttons.

To answer the request, uncheck the entries your answer should leave out, decide whether to remember it, and press **Allow** or **Deny**:

[cols="2,2,3"]
|===
|Answer |This request |Later requests

|**Allow**
|The checked entries are handed out.
|Everything is asked again.

|**Allow** with **Remember**
|The checked entries are handed out.
|The checked entries are allowed without asking.

|**Allow** with **Remember** and future entries
|Every listed entry is handed out.
|Everything this client asks for is allowed without asking, including entries created later.

|**Deny**
|Nothing is handed out.
|Everything is asked again.

|**Deny** with **Remember**
|Nothing is handed out.
|The checked entries are denied without asking.

|**Deny** with **Remember** and future entries
|Nothing is handed out.
|Everything this client asks for is denied without asking, including entries created later.
|===

An unchecked entry is never part of the answer: it is not handed out now, and the client is asked about it again the next time.

An answer about future entries covers the listed ones as well and can only be a stored one, so checking that row checks every entry and turns **Remember** on. To make an exception for a single entry, change its decision afterwards as described in <<Managing Stored Decisions>>.

A request for entries of several databases is asked one database at a time, in one dialog after the other. Each answer is stored in the database it was given for, and its future entries row covers that database only.

A stored answer applies to the same client from then on, across restarts of both KeePassXC and the client. This is what makes short-lived clients such as `secret-tool` workable with confirmations turned on: the client is recognized by what it is, rather than by the process it happens to run in. How that recognition works, and when to distrust it, is the subject of the next sections.

==== How the Client Is Recognized

A stored answer has to recognize the client when it asks again — later, and from a different process. While **Remember** is checked for a client KeePassXC has not stored anything for yet, the text next to it says what the client will be recognized by. **Change…** there, or **Details**, shows what that is built from:

.Access Request Details
image::secretservice_access_details.png[]

Each row is one process. The request comes from the bottom row; the row above it is the process that started it, and so on up to the top of the session. For every process the tree shows its name, process ID, executable path, and command line. A warning icon on the executable marks content that changed since access was stored.

The **Match** column selects what the stored answer is anchored on. For each ticked process, KeePassXC records the executable path and a digest of the executable content, and a later request matches only when the process at the same position satisfies both. The digest is what makes an updated binary ask again. KeePassXC ticks only the requesting process itself; whether any ancestor identifies the client is your judgment to make, weighed in the next section. With **Remember** unchecked nothing is stored, and the column is hidden.

Once an answer is stored, the client is known. The next request from it is marked **Known** and says since when, and the **Match** column shows what its stored rule compares for each process: path, name, content, or nothing. The rule of a known client is not changed from this dialog; see <<Managing Stored Decisions>>.

The notes below the client's name point out what deserves a second look:

* **Unverified executable**: the executable path is missing or unreadable, so the client cannot be identified reliably.
* **General purpose tool**: the caller is a script interpreter such as `python3`, a shell, or a command line client such as `secret-tool`. It asks on behalf of whatever invoked it, so a stored decision would authorize every use of that tool by any program.
* **Changed executable**: the executable content differs from what was recorded when access was stored. This is what an update of the client looks like, and also what an impostor at the same path looks like, so the decision has to be made again. Remembering the new decision accepts the changed executable as this client.

When any of these apply, the client is marked along its edge, the details start expanded, and **Remember** starts unchecked, which is also the recommended answer. Checking it anyway lists what storing the decision would do right below it.

==== Narrowing a Decision With an Ancestor

There is a way to narrow a stored decision further, and it fits one shape: an ancestor that has an executable of its own and exists to do a single job, which reaches for a secret through a general purpose tool. A compiled program of yours that calls `secret-tool` is such an ancestor. Ticking it in the **Match** column adds it to the rule, which from then on matches only clients started by it.

A script is not such an ancestor. Running a script executes its interpreter, so the executable of that process is `/bin/bash` or `/usr/bin/python3`, and that is what a condition on it would match — the general purpose tool again, under a different name. Which script is running appears only in the command line, which is shown in the details for you to read and is never matched on: a process can rewrite its own command line at will.

Conditions apply to a position in the process tree, not to the tree as a whole. A condition on the parent matches clients whose parent is that executable, and one two levels up matches clients exactly two levels below it. Anchoring on `init` therefore does not cover everything in the session, and a rule stops matching when the same program is started through a different chain, from a terminal instead of a service, for example.

Judgment is what makes this work, and general purpose tools are a broader family than script interpreters: shells, `secret-tool`, `dbus-send`, `busctl`, `xargs`, `env` and anything else that runs or asks on behalf of whoever called it. When the ancestor you are about to tick is one of those, the rule has not become any narrower. When in doubt, leave **Remember** unchecked.

WARNING: A rule you write yourself is applied exactly as written. Use at your own risk.

=== Managing Stored Decisions
Stored decisions live in the database they concern, and everything the access request stores can be reviewed and changed later.

**To see or change what a client may access**, open **Database → Database Settings → Secret Service**. Each row under **Client Authorizations** is one client the database recognizes, with the rules that recognize it and a summary of its decisions:

.Client Authorizations
image::secretservice_database_settings.png[]

**Edit** opens the client:

.Client Authorization Editor
image::secretservice_client_record.png[]

The upper half holds the matching rules. A client matches when it satisfies every condition of at least one rule. Each condition applies to one process of the requesting process tree — the caller, its parent, and so on — and requires a matching executable path, executable file name, or SHA-256 digest of the executable content. **Hash from File…** fills a digest condition from an executable on disk, for example after the client was updated. Digests are what turn an update of the client into a new access request; paths and names alone do not.

The lower half holds the decisions: the entries with a decision of their own, and under **All other entries**, the decision covering everything else — this is where an answer that includes future entries ends up.

TIP: Two clients can be written so that the same application matches both. KeePassXC points this out and resolves it in a fixed order — a record denying everything wins, otherwise the record created first — but it is worth removing the ambiguity.

**To change the decisions on a single entry**, edit the entry and open its **Secret Service** page. The same decisions appear here grouped by entry rather than by client, where they can be changed, removed, or added for a client the database already knows:

.Entry Access Decisions
image::secretservice_entry_settings.png[]

**To see which clients are connected right now**, open **Tools → Settings → Secret Service**. The **Authorization** column shows which stored client each connected application is recognized as in each open database, or that its executable changed, and it will be asked again:

=== Limits of Client Recognition

WARNING: A stored decision is a convenience, and it is not an authentication mechanism. Understand what it can and cannot tell apart before you store one.

A client is recognized by its executable path and by the content of that executable, read through `/proc`. That much survives the client restarting or getting a new process ID, and it tells an updated or replaced binary from the one that was authorized.

Everything below defeats it:

* Code injected into a legitimate client, for example through `LD_PRELOAD` or a plugin it loads, runs as that client and inherits its authorizations.
* Two scripts run by the same interpreter look identical: both processes run the interpreter's executable, and the script's path is part of the command line, which is not matched on. Only an ancestor with an executable of its own can tell them apart.
* A process whose executable `/proc` does not reveal, such as one with `PR_SET_DUMPABLE` cleared or one owned by another user, is never recognized and asks every time.
* Any user who can write the client's executable, or place their own executable at that path, becomes that client as far as KeePassXC can tell.

Grant a stored decision the way you would grant the password itself: to a program you would hand it to anyway.

=== Implementation Details

* The user can specify the database and group that is exposed to the service.
* Desktop notifications when a secret is retrieved and access confirmation dialogs.
* `FdoSecrets::Service` is the top level DBus service. There is one  `FdoSecrets::Collection` per opened database tab and each entry under the exposed database group has a corresponding `FdoSecrets::Item` DBus object.
* The following entry attributes are exposed to the secret service: Title, Username, Password, URL, Notes, TOTP, and non-protected Custom Attributes.
* Stored decisions are kept in the database: the client and its rules in the database's custom data, the decision for an individual entry on that entry. Older KeePassXC versions keep them intact, but merging a database with one of those versions can drop them, in which case the client asks again.
